# Критические проблемы

tags: #ponchi #audit #blockers
updated: 2026-04-16

## P0 — блокирует релиз

### 1. `menu` и `orders` еще не backend-driven

- Клиент меню ходит в публичный JSON через `MenuRemoteDataSource`.
- `POST /v1/orders` и `GET /v1/orders` описаны в `docs/api/contract.md`, но не реализованы в коде клиента и `ponchi-functions`.
- `OrderViewModel` пока работает только с локальными массивами `activeOrders` и `completedOrders`.

Почему это критично:

- App Store релиз без реальных заказов для кофейного приложения ломает основной продуктовый сценарий.

### 2. Auth начат, но не доведен до production-ready состояния

- `auth-request-code` создает код в БД, но не отправляет реальную SMS.
- Нет `refresh token`, revoke/logout endpoint и delete account flow.
- В `SessionManager` хранится только access token.

Почему это критично:

- пользовательский аккаунт и сессия для боевого приложения должны быть управляемыми и устойчивыми.

### 3. Частично недоведенный release-конфиг

- `AppConfig` уже есть, но `PonchiApp.swift` все еще хардкодит `menuURL`.
- `YMKMapKit.setApiKey(...)` все еще захардкожен.
- `Info.plist` не содержит `YandexMapsAPIKey`.
- В `Release` build setting для `PONCHI_MENU_URL` сейчас виден дублированный URL с переносами строк.

Почему это критично:

- релизный конфиг должен быть предсказуемым, иначе баги будут зависеть не от кода, а от режима сборки.

### 4. Доменные баги в товаре / корзине / бонусах

- `Ponchi.id` и `Equatable` не учитывают `selectedTeaType`.
- `comment` есть в UI, но не живет в модели.
- `hasTeaType` проверяет `selectedTeaType`, а не наличие `teaType`.
- `bonusPoints` и `user.bonuses` дублируют источник истины.

Почему это критично:

- это приводит к неправильной корзине, неверному UI и плавающему поведению.

## P1 — высокий риск, но не мгновенный стоппер

### 1. Перегруженные `ViewModel`

- `UserViewModel` одновременно держит auth, профиль, избранное, бонусы, sheet state и часть UI-навигации.
- `PonchiViewModel` держит меню, detail state, комментарий, баннер офлайна и часть cart-related логики.

Почему это опасно:

- чем дальше проект, тем сложнее тестировать и менять такие объекты без побочных эффектов.

### 2. UI-долг на экранах профиля и заказов

- В профиле есть пустая ветка рендера аватара.
- Кнопки “почта для чеков” и “напишите нам” декоративные.
- Экран заказов не имеет настоящих server-driven статусов и пустых состояний на реальный сценарий.

### 3. Отсутствие тестов и observability

- Нет unit-tests.
- Нет UI-tests.
- Нет crash reporting.
- Нет аналитики и ключевых событий по auth/order.

## P2 — технический долг

### 1. Репозиторий и структура

- Вложенный `Ponchi-clean`.
- `Utilites/Preview ` с пробелом в имени папки.
- Дубли UI-компонентов.
- Неиспользуемые legacy-файлы.

### 2. Зависимости и ресурсы

- `BottomSheet` одновременно присутствует как исходники и как pin в `Package.resolved`.
- В app bundle попадает `BottomSheetSwiftUI.podspec`.
- В шрифтах есть `Kica-PERSONALUSE-Light.ttf`.
- В проекте лежит `GoogleService-Info.plist` без активного Firebase integration.

## Отдельные точечные находки

### Бизнес-логика

- `PonchiCartView` очищает корзину после `order.placeOrder(from:)`, хотя `placeOrder(from:)` уже сам очищает корзину.
- `useBonus(for:)` уменьшает `currentUser.bonuses`, но не публикует обновленный `user`.
- `PonchiBonusView` вообще не встроен в основной flow и выглядит как dead code.

### UI / UX

- В `README` заявлен поиск, но search-layer в коде я не нашла.
- `PonchiMenuScrollView` использует фиксированную сетку `180x280`.
- `SplashView` использует старый video-based flow, но фактически приложение стартует через `LaunchScreenView`.

### Release

- `PRODUCT_BUNDLE_IDENTIFIER = come.ponchi.app` выглядит как опечатка.
- `Podfile` минимальная iOS `13.0`, а target сейчас `17.0`.
- Карта доступна только в `Release`, что создает различие между debug и release-поведением.
